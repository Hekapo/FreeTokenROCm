# Исследование скорости после обновления ROCm — 13 октября 2026

## Что установлено

У воспроизведённого медленного режима есть управляемый фактор: размещение
потоков backend по логическим процессорам CPU. Разрешение одного логического
процессора на каждое физическое ядро ускорило тот же запрос на **25–28%**.
При возврате исходной affinity скорость снова снижалась. Два переключения
выполнены в одном процессе, с одинаковыми библиотеками, моделью и ответами.

Вероятный механизм — конкуренция потоков backend и HIP runtime за ресурсы
одного физического ядра при SMT. Эксперимент доказывает эффект affinity;
точное размещение отдельных потоков во время прежнего soak не записывалось.
Поэтому прежнее снижение **50,02 → 39,06 токен/с** нельзя считать полностью
объяснённым на уровне конкретного потока или момента переключения.

Само обновление библиотек выигрыша скорости в парном коротком сравнении
не показало: ROCm 10.0 / Torch 2.13 / Triton post28 — **37,20 токен/с**,
ROCm 10.1 / Torch 2.14 / Triton post29 — **36,17 токен/с**. Разница −2,75%
сопоставима с разбросом трёх повторов. Это последовательное A/B, а не полная
ABBA-квалификация версий; статистически значимый регресс этим не доказан.

## Условия и результаты

- RX 9070 XT, gfx1201/wave32; Ryzen 7 9700X, 8 ядер / 16 логических процессоров.
- Windows 11 24H2, существующий драйвер; схема питания «Сбалансированная».
- Одни исходники main `3b8bdecbfb107cd0e55f79cc3d57a410c9bcb107`, один GGUF
  Qwen3.6-35B-A3B-Q4_1, BF16, offload/LRU 2048, graphs 0, concurrency 1.
- Контекст и KV 65536; входы диагностики не длиннее 489 токенов.
- Одинаковые 32 коротких прогрева, затем три контрольных запроса.
- Контроль: 24 входных / 391 выходной токен, одинаковый SHA256 текста,
  greedy, без reasoning. По одному запросу cProfile на стек исключены из скорости.
- Статистика backend собиралась одинаковым наблюдателем; ADL-сэмплер в
  парном сравнении не запускался.

| Блок на новом стеке | Affinity backend | Токен/с, медиана 3 запросов | CPU подготовка шага, мс |
| --- | --- | ---: | ---: |
| Исходный режим | Все 16 LP, `0xFFFF` | 36,17 | 27,00 |
| Ограничение 1 | Один LP на ядро, `0x5555` | 46,74 | 20,51 |

Прирост относительно соседнего блока возврата: **+28,09%** и **+25,23%**.
Доля промахов MoE-кэша во всех четырёх блоках переключения одинаковая:
**0,14946717817561808**. GPU stream metric около 1,53–1,58 мс не уменьшился.
Время рабочего потока CPU близко ко всему wall time подготовки шага.
Это подтверждает влияние CPU, без объяснения прироста улучшением MoE hit rate.

Топология прочитана через Win32, а не выведена из нумерации процессоров:
маски физических ядер `3,12,48,192,768,3072,12288,49152`.
Выбрано по одному LP из каждого ядра. Менялась affinity только backend,
с точной проверкой PID, времени создания, executable и принадлежности
записанному дереву. Исходная маска возвращалась после каждого блока и в finally.
API и смысл масок сверены с [документацией Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask)
и [описанием топологии](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-system_logical_processor_information).

## Проверки и текущее состояние

**84/84** запроса сравнения корректны: 36 на старом стеке и 48 на новом.
Независимый verifier проверил порядок запросов, usage, hashes, backend UID,
повторные переключения, ресурсы, runtime hashes и Stop. Все 31 записанная
идентичность процессов двух успешных запусков завершилась. KV в конце — 0.

Пороги запуска 38/45/14, работы 12/4/3 и восстановления 38/28/14 сохранены.
После последнего Stop: RAM 49,685 / commit 47,853 / GPU free 14,829 GiB.
Штатный сервис STOPPED, порт свободен, recovery_required=false.
Повторный Verify подтвердил 476 исходников, 74 пакета и 5 native files.

сохранён. Все 124 Python-файла установленного Triton post28/post29 совпали.

CPU профиль показал 381 Triton launch на шаг и 1813 tensor-specialization

381 раз на шаг; он имеет небольшой CPU расход. Это не объясняет весь
воспроизведённый медленный режим, который есть и на старом стеке без hook.

## Сбои диагностики, которые сохранены

1. Первый новый probe завершил 36 коротких запросов, но длинный вход 63488
   остановился после 54272 обработанных токенов. После 45 секунд без прогресса
   клиент закрыл запрос. Затем controller и observer получили таймаут проверки
   процессов: около 29,5 секунды при лимите 5 секунд. Managed Stop не прошёл.
   Записанные процессы позднее завершились; порт, RAM, commit и GPU независимо
   проверены. Исходный fault marker и данные запуска сохранены в
   `.local/speed1010-new`. **Причина этого stall не установлена**; CPU affinity
   не проверялась на данном входе и не считается исправлением этого сбоя.
2. Первый короткий повтор нового стека не дошёл до клиентских замеров:
   после старого запуска оставался включённый флаг профилирования. Стартовая
   проверка создала пустой cProfile, который отверг `pstats.Stats`. В сценарий
   добавлен сброс флага перед Start; повтор выполнен в свежем каталоге,
   48 запросов прошли. Оба исходных результата сохранены.

В System/Application не найдено сообщений о сбое драйвера в окне первого
stall; журнал WMI Activity был выключен. Это отсутствие доступных записей,
а не доказательство отсутствия проблемы драйвера или ОС. За ПК в это время
пользователь не находился. В реестре прочитан TdrDelay=8; настройки не менялись.

## Следующий шаг на момент диагностики

Добавить в штатный launcher явный режим **backend CPU affinity: один LP
на физическое ядро** с определением топологии Win32 и логированием выбранной
маски. Режим должен применяться только к backend и позволять возврат к
обычному распределению Windows. В этой диагностике настройка временная;
изменение штатного запуска ещё не реализовано.

Позднее режим перенесён в repository launcher и включён в локальном запуске.
[Отдельный отчёт внедрения](rocm1010-cpu-affinity-launcher-20261013.md)
содержит проверку bootstrap, четыре коротких counting-запроса и чистый Stop.
Данные этой диагностики остаются исходным результатом временного A/B.

Для принятия этого режима достаточно сначала одной короткой проверки
репозиторного launcher. Длинный prefill и смешанная нагрузка с affinity
ещё не квалифицированы. Вопрос первого длинного stall остаётся открытым;
следующий длинный запуск требует отдельной диагностики с захватом стека
и последней операции GPU. Новую полную серию здесь не проводили.
