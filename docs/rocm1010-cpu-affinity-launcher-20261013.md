# CPU affinity в штатном запуске 64K — 2026-10-13

Режим `one_per_core` перенесён в репозиторный launcher и включён в локальных
`config.json` и `config-rocm1010.json`. Реализация проверена в ветке
`integration/backend-cpu-affinity`. Исходники движка, 74 пакета и пять
проверяемых native/compiler файлов сохранены. Workaround ROCm10.1 остаётся
прежним: SHA256 `c30250abfaa0ee14e744e84628458d0f423d82f63759525c5be0591fbd63b19d`.

## Реализация

- Schema3 хранит `backend_cpu_affinity`: `windows` или `one_per_core`.
  Schema1/2 читаются с размещением Windows, без перезаписи конфигурации.
- `SetCpuAffinity` проверяет остановку сервиса, общий mutex, порт, reviewed
  release и топологию CPU, затем атомарно сохраняет настройку без модели.
- Win32 определяет физические ядра и выбирает один доступный LP на ядро
  внутри наследуемой маски. Число ядер и маска не зашиты в код.
- Изменение применяется только в single-rank scheduler/backend до
  инициализации GPU. На Ryzen7 9700X это `0xFFFF` → `0x5555`: 16 → 8 LP.
  Родительский процесс, frontend и tokenizer сохраняют `0xFFFF`.
- Module-level spawn target сохраняет совместимость с Windows
  multiprocessing. Receipt записывает PID, время создания, топологию и маску;
  launcher сверяет их с живым процессом до принятия readiness.
- Ошибки API, неизвестный bootstrap, несовпадение receipt и несколько
  processor groups для `one_per_core` останавливают запуск. Режим `windows`
  позволяет вернуться к исходному размещению после Stop.

Команды выбора и возврата приведены в
[руководстве запуска](run-windows-rocm64k.md#backend-cpu-placement).

## Проверка

96 CPU-проверок прошли за 17,65 с. Среди них реальный Windows spawn без Torch:
маска backend меняется и восстанавливается, а parent/tokenizer сохраняют
наследуемую маску. Проверены отказ при ошибке API, схема конфигурации,
запрет переключения при активном сервисе, PID/time и live-affinity receipt.

Короткий запуск выполнен на замороженной копии текущего repository launcher
с обычным ROCm10.1 / Torch2.14 / Triton3.8.post29. Context и KV — **65536**.
Один встроенный readiness-запрос, один прогревочный и три измеряемых запроса
прошли. Все четыре counting-ответа содержат 391 токен при prompt24, совпадают
с сохранённым SHA256, завершаются `stop`; после запросов used KV pages = 0.

Медиана TTFT — **0,750 с**. Скорость согласуется с прежним обратимым эффектом
CPU placement: в [исследовании](rocm1010-speed-investigation-20261013.md)

контролируемым A/B или доказательством ускорения SDK.

## Память и Stop

По явному разрешению пользователя текущая короткая проверка использовала
разовое исключение для startup commit. Перед успешной попыткой доступно
43,346 GiB commit; только в отдельной копии launcher порог был 40 вместо45.
Прочие startup-пороги 38 GiB RAM / 14 GiB VRAM и runtime12/4/3 сохранены.
Start атомарно расходовал разрешение; повторный Start этой копии запрещён.
После Stop копия profile и его проверка возвращены к45. Постоянный
репозиторный профиль всё время сохранял45 GiB.

По 69 resource samples минимум доступных RAM/commit/VRAM:
**21,206 / 8,983 / 6,575 GiB**. После Stop:
**46,489 / 43,328 / 14,809 GiB**. Контроллер подтвердил STOPPED, отсутствие
listener/owned tree и recovery marker. Независимая сверка всех 23 записанных
PID/time не нашла оставшихся процессов.

Первая попытка загрузила модель, подтвердила affinity и readiness, но мой
counting-клиент не передал `stats_poll_s`. Запрос был отменён, Stop прошёл
чисто. Клиент исправлен; до следующей загрузки проверено наличие всех
параметров request-helper. Повтор выполнен в свежем каталоге в рамках той
же короткой проверки. Первые данные и исходный клиент сохранены; все22
зафиксированные процессные идентичности первой попытки также исчезли.

После успешной проверки оба локальных ROCm10.1 config переключены на
`one_per_core`. `Verify` подтвердил исходники/пакеты/native hashes и порог45,
`Status` — STOPPED. Rollback-конфигурация ROCm10.0 сохраняет `windows`;
её Verify тоже прошёл без модели. Новые Configure по умолчанию выбирают
`windows`; выбор режима остаётся явным.

## Область результата и данные

Длинный prefill, смешанная нагрузка и soak с новым режимом не запускались.
Первый длинный stall остаётся открытым; его fault marker и отчёты сохранены.
Эта короткая проверка не доказывает исправление stall или общего падения
скорости в прежнем soak. Для повторной полной серии сейчас оснований нет.

содержит receipt, живые маски всех процессов, измерения, ресурсные минимумы,
разовое разрешение и SHA256 сырых доказательств.
