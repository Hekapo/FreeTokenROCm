## Обход ошибки компилятора

Исходный post29 по-прежнему неверно сворачивает histogram comparisons,
динамический цикл 0/1 и вложенный цикл с расширением границ.
Native compiler не исправлен.

[compiler_safety.py](../scripts/windows-rocm1010/compiler_safety.py) использует
штатный `triton.knobs.runtime.add_stages_inspection_hook`. Адаптер создаёт
копию проверенной Python-функции `make_ttgir` и исключает ровно один вызов
`tritonamdgpu-fold-true-cmpi`. Установленные файлы Triton и native DLL не меняются;
глобальная регистрация compiler pass не подменяется.

Адаптер включается только явным вызовом до GPU initialization. Он проверяет
версии Torch/SDK/Triton и SHA256 исходного AMD compiler/pipeline, ограничен
`gfx1201` / wave32 и отказывается заменять чужой hook. Собственный ключ hook
участвует в Triton compilation cache key: исходный и изменённый варианты
четырёх одинаковых kernels получили разные cache hashes.
Обычный лаунчер этот адаптер не импортирует и не включает.

Штатный механизм описан в
[примерах Triton](https://github.com/triton-lang/triton/blob/main/examples/plugins/README.md).
Исходные дефекты и backports: [histogram 11577](https://github.com/triton-lang/triton/pull/11577),
[loop range 11429](https://github.com/triton-lang/triton/pull/11429).
Обход не является включённым upstream исправлением или доказательством
корректности любых kernels.

## Выполненные проверки

- 12 CPU unit tests адаптера: сохранение соседних passes, отказ при неизвестной
  форме pipeline, неподходящем комплекте/hash, существующем hook и поздней
  установке; импорт без автоматического включения GPU-библиотек.
- Четыре полноценных compile-only reproducer до и после обхода: histogram
  `1024/64`, histogram `4096/128`, динамический и вложенный циклы. В исходном
  варианте ошибки воспроизвелись; после обхода нужные predicates/comparisons
  сохранились. GPU в compile-only процессе не инициализировался.
- Пять небольших GPU checks: те же четыре kernels с точным CPU-reference,
  включая пустые histogram bins и незаписанные sentinel slots, плюс FP32 GEMM.
- Шесть существующих GPU tests: nucleus sampling с vocab 1000/151936,
  GDN partial chunk/recurrent с геометрией `H=32, Hg=16, K=V=128, T=65`,
  GGUF Q4_0 dequantization, matvec и routed MoE. Все прошли.
- В кэше 19 compiled Triton variants; максимальный shared memory -- 36864 bytes
  (36 KiB), ниже предела 64 KiB. Это относится к проверенным shapes.
- GGUF native extension отдельно собран для текущего candidate; его SHA256
  включён в manifest. Пять vendor native hashes после диагностики совпали
  с начальным snapshot.

GPU-процесс работал около 117 секунд, включая компиляцию native extension,
завершился с exit code 0 и не оставил процесс или слушателя сервера.
Предупреждения касались deprecation `tl.make_block_ptr` и приватного helper
setuptools `_get_vc_env`; ошибок вычисления или сборки не было.

## Продолжение: Q4_1, attention и короткий запуск 64K

Дополнительная GPU-диагностика `--suite q4-attention` прошла: **3 passed**.
Q4_1 MoE gate/up и down проверены на границе GPU grid с CPU-reference и split
вариантом: 8 experts, 8192 tokens, 8 routes. Attention prefill и decode проверены
с BF16 на геометрии GGUF модели: 16 query heads, 2 KV heads, head size 256,
разные lengths/prefixes в paged KV. Пик Torch allocated/reserved --
84716544/144703488 bytes. Начальный commit45.269 GiB, после45.239 GiB.

Для модели подготовлен отдельный managed runtime из проверенных 17 файлов
обычного контроллера. Добавлены проверенный compiler adapter, явный
`sitecustomize` bootstrap и Q4_1/attention proof. Новый runtime сверяет
476 engine files, 74 packages, пять native hashes и собственные 20 файлов;
он использует общий mutex и port1919. Старые long/capacity evidence не
выдаются за квалификацию нового native комплекта.

Windows multiprocessing использует spawn: compiler hook устанавливается
отдельно в каждом процессе перед импортом `freetoken.kernel` и GPU
initialization. Флаг AMD buffer ops закрепляется там же. CLI/helper процессы,
которые не импортируют kernels, не загружают Torch через bootstrap.
Ошибка установки завершает процесс с кодом86. CPU-проверки bootstrap --
**3 passed**, включая spawn и неправильную версию Torch; bounded smoke client
-- **4 passed**, включая неправильную KV capacity, ответ и ошибку stream.

### Исправление пути JIT-сборки

Первый старт загрузил модель, но readiness request получил503: MSVC linker
не мог создать DLL `fast_index_copy` и выдал LNK1104. Выходной путь был
**289 символов**. Независимая линковка без модели и GPU с тем же object file
воспроизвела ошибку при289 символах и прошла при119 символах.

`prepare_trial.py` теперь принимает `--state-root` для короткого свежего
каталога state/cache и проверяет длину ожидаемого DLL пути до создания
runtime. Повтор прошёл с state в `.local/rocm1010/smoke-20261012` от общего
workspace. Caches остаются отдельными для каждого запуска. Отчёт, fatal
marker и логи первого сбоя сохранены; этот старт не учитывается как успешный.

## Повторение

Проверка без GPU; каждый output directory должен быть новым:

```powershell
& <candidate-python> -B scripts/windows-rocm1010/qualify_compiler.py --output <fresh-output>
```

GPU-диагностика требует настроенного обычного 64K launcher и явного разрешения
на текущую ОС/драйвер. Wrapper удерживает общий mutex сервиса, проверяет запас
памяти, контролирует runtime floors и завершает своё дерево процессов при
ошибке или timeout 240 секунд. После успешного прогона добавлены обработка
abandoned mutex и проверка Stop request; изменения проверены parser без GPU.

```powershell
pwsh -NoProfile -File scripts/windows-rocm1010/qualify_gpu.ps1 `
  -VenvRoot <isolated-candidate-venv> -Output <fresh-output> `
  -ProjectOperators -AllowUnqualifiedHost
```

Для отдельных Q4_1/attention contracts к команде добавить `-Suite q4-attention`.
Для пробного managed runtime после этих проверок:

```powershell
& <candidate-python> -B scripts/windows-rocm1010/prepare_trial.py `
  --venv <isolated-candidate-venv> --output <fresh-trial-runtime> `
  --state-root <fresh-short-state-path> --operators <q4-attention-output>
pwsh -NoProfile -File <fresh-trial-runtime>/runtime/service64k.ps1 `
  -Action Verify -ConfigFile <fresh-short-state-path>/config.json
```

`Start` и `Stop` используют тот же controller/config. При запуске клиента
`scripts/windows-rocm1010/smoke_request.py --output <fresh-result.json>`
Stop должен выполняться в `finally`. Подготовка по умолчанию сохраняет
startup commit45 GiB; исключение текущего запуска не переносится в генератор.

Текущий запуск был явно разрешён пользователем. Windows 11 24H2 / build26100,
RX9070XT и DriverStore32.0.31041.1004 отличаются от строки
[матрицы AMD 10.1](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html):
25H2 / DriverStore32.0.31041.5005. Результат помечен вне этой vendor строки;
ОС и драйвер не обновлялись.

Локальные исходные отчёты: `rocm10-20260926/research-refresh-20261011-audit/deps-upgrade-20261012`
относительно workspace. Manifest сохраняет их hashes. Исторические отчёты
этапа 5 и данные прежнего запуска сохранены.

## Штатное применение13.10.2026

Ветка `integration/rocm1010-upgrade`. Один контроллер теперь читает выбранный
runtime из config schema2; schema1 совместим и означает10.0. Новые конфигурации
по умолчанию выбирают10.1. Отдельные release/source manifests проверяют
74 packages и пять native hashes для каждого варианта. Новый release проверяет
19 runtime inputs, точные Q4_1/attention/model/Stop evidence и compiler hook;
старый сохраняет17 runtime inputs и исторические10.0 evidence. Численный
engine source476files, profile capacities и пороги не менялись.

Bootstrap в `scripts/windows-rocm64k/rocm1010` имеет те же bytes, что проверенный
пробный adapter/bootstrap. Установка происходит до GPU initialization в каждом
spawned kernel процессе. Старый вариант очищает opt-in env flags и запускается
со своим source/environment manifest. Stop, ownership checks, mutex и observer
общие. Успешный старт теперь сохраняет `startup-result.json`.

CPU-приёмка: **33 controller/source/config tests + 9 candidate-proof tests**.
Исходные6 failing contracts перед реализацией сохранены отдельно; ошибки
общего kernel-teardown fixture в первоначальной настройке тестов также

окружений. Подготовка отдельного snapshot теперь повторно использует
проверенный общий контроллер; её Verify также прошёл без модели.

Default config заменён атомарно под общим mutex после проверки STOPPED.
Оригинальный schema1 config сохранён. Оба новых state roots короткие и
раздельные, внутри общего workspace `.local/service64k-rocm1010` и
