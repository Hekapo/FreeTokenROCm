# FreeTokenROCm: подготовка безопасной миграции ROCm

## Статус этого пакета

Это подготовительный пакет, а не выполненная миграция и не подтверждение совместимости ROCm 10.0 с конкретной рабочей средой.

В текущей сессии прочитаны опубликованные ветки, `pyproject.toml`, `setup.py`, `python/freetoken/kernel/_toolchain.py`, `docs/install.md`, `AGENTS.md` и `CONTRIBUTING.md` репозитория `Hekapo/FreeTokenROCm`.

Ничего не изменено в GitHub. Ветки, коммиты и PR не создавались. Драйверы, зависимости, рабочая среда пользователя и веса моделей не изменялись.

Созданы отдельный диагностический скрипт и его тесты. В Linux-среде помощника прошли **8 unit-тестов** и запуск без GPU-проверки. Windows-ветка получения объёма RAM и реальная проверка PyTorch/HIP на RX 9070 XT здесь не выполнялись. Скорость FreeToken не измерялась.

## 2. Конкретные точки проверки, найденные в коде

### 2.1. CUDA-источник PyTorch в конфигурации uv

В `pyproject.toml` источник `torch` привязан к `pytorch-cu130`, а индекс указывает на CUDA wheels. Это риск для операций uv, которые учитывают `[tool.uv.sources]`, а не доказательство, что уже установленная среда пользователя неправильная.

**Предлагаемое изменение:** сделать выбор источников явным для CUDA и ROCm. Установка AMD-профиля не должна молча заменять AMD PyTorch на CUDA или CPU wheel. После установки проверять `torch.version.hip`, фактическую доступность GPU и его архитектуру. Не удалять CUDA-путь, если форк продолжает его поддерживать.

### 2.2. Ограничения версий и документация расходятся

`pyproject.toml` задаёт `torch>=2.11,<2.14` для build/runtime и `triton>=3.6,<3.8` на Linux. В `docs/install.md` инструкция ещё упоминает `torch>=2.11,<2.12` и ROCm 7.14.

**Предлагаемое изменение:** согласовать документацию и профили зависимостей с реально выбранными официальными wheels. Не расширять диапазоны наугад. Особенно проверить, какой Triton требует выбранный PyTorch и доступен ли он для нужной ОС/Python.

### 2.3. Поиск HIP SDK и согласованность инструментов

`ensure_rocm_env()` сохраняет уже заданный `HIP_PATH`; при его отсутствии пытается обнаружить `_rocm_sdk_core`. CUDA-проверка согласованности компилятора и torch пропускается для ROCm. Это не равнозначно полной проверке согласованности HIP runtime, SDK и PyTorch.

**Предлагаемое изменение:** диагностировать, откуда берутся SDK, компилятор и runtime. Старый `HIP_PATH`/`ROCM_HOME` не должен незаметно направлять новое окружение в прежний SDK. Не требовать простого равенства номеров HIP и ROCm Core SDK: версии компонентов могут иметь собственную нумерацию.

### 2.4. Native extensions нельзя считать изолированными одним venv

`setup.py` собирает `_pinned_tensor` и `_cpu_moe` с линковкой HIP runtime. В проектных инструкциях используется и сборка `--inplace`.

**Предлагаемое изменение:** использовать отдельную копию исходников/worktree для новой среды, отдельные каталоги сборки и JIT-кэшей. Не переиспользовать старые `.so`/`.pyd` или очищать общий кэш рабочей среды. Расширения пересобирать с выбранной версией PyTorch/SDK.

### 2.5. Disk PLE зависит не только от ROCm

В этом `setup.py` расширение `_ple_store`, используемое для disk PLE, включается только на Linux.

**Следствие:** установка ROCm 10.0 сама по себе не добавляет native Windows disk PLE. Подготовку миграции окружения и перенос этого функционала нужно вести раздельно. Это особенно важно для будущих экспериментов с Qwen3.8-Flash-Next и ограниченной RAM.

## 3. Цель первого этапа

Подготовить **изолированный кандидат на ROCm 10.0.0**, сохранив текущую 7.2.1 как контрольную среду.

Официальные release notes ROCm 10.0.0 существуют и перечисляют поддержку PyTorch 2.13.0. Но для установки нужно отдельно выбрать официальный набор wheels/образ под фактические ОС, Python, GPU и совместимый драйвер. Этот пакет не содержит непроверенного универсального `pip install` и не объявляет совместимость FreeToken доказанной.

Nightly 10.1 не является обязательной частью миграции. Её имеет смысл оценивать позднее, отдельно, если потребуется конкретный отсутствующий в стабильной версии механизм.

**Важно:** venv изолирует Python-зависимости, но не системный видеодрайвер, не все системные библиотеки и не общие JIT-кэши. Контейнер также использует драйвер хоста. Полный откат нельзя обещать только на основании сохранённого каталога venv.

## 4. Что можно сделать без AMD GPU

Подготовить небольшие отдельные изменения, каждое с тестами:

1. Диагностика окружения: ОС, версии пакетов, PyTorch backend, архитектура, SDK-пути, Git SHA; понятные ошибки вместо скрытого fallback.
2. Явные AMD/CUDA-профили установки, проверка конфликтов ограничений, фиксация проверенных источников пакетов.
3. Проверки поиска toolchain, пользовательских override и изоляции build/JIT-кэшей.
4. Документация установки, отката и протокол измерений.
5. Выборочный аудит исправлений upstream/Maxritz; переносить только после проверки, что исправление ещё отсутствует и подходит текущей архитектуре форка.

Не совмещать большой merge upstream, изменение ядер, обновление драйвера и миграцию Python-окружения в один этап. Иначе трудно определить источник ускорения или регрессии.

Предполагаемые рабочие файлы: `pyproject.toml`, `docs/install.md`, `python/freetoken/kernel/_toolchain.py`, при необходимости `setup.py`; дополнительные скрипты и тесты создавать в соответствии со структурой репозитория. Это список будущих изменений, а не уже применённый patch.

## 5. Проверки на компьютере пользователя

### Этап A — снимок контрольной среды

Запустить приложенный `collect_rocm_env.py` именно Python-интерпретатором рабочего окружения FreeToken, а не случайным системным Python.

Из каталога подготовительного пакета:

```text
python collect_rocm_env.py --repo "ПУТЬ_К_РЕПО" --label baseline-7.2.1 --out rocm-baseline.json
```

Это читает metadata пакетов и Git-состояние, но не импортирует torch и не запускает GPU.

Дополнительная проверка доступности GPU:

```text
python collect_rocm_env.py --repo "ПУТЬ_К_РЕПО" --label baseline-7.2.1-probed --probe-torch --out rocm-baseline-probed.json
```

`--probe-torch` импортирует PyTorch в дочернем процессе и перечисляет GPU. Это может инициализировать HIP/потребовать память, поэтому проверку лучше выполнять после остановки тяжёлой генерации. Она не загружает модель и не проверяет корректность ядер.

Скрипт не устанавливает пакеты, не делает fetch/push/commit, не читает `.env`, Git remote URLs, содержимое исходников или diff. Отчёт создаётся только по указанному пути; существующий файл не перезаписывается. Домашний путь маскируется, но остальные пути могут остаться — проверить JSON перед отправкой. Точные пути реально загруженных DLL/SO и версия драйвера этим скриптом не измеряются.

### Этап B — подготовка новой среды

Уточнить драйвер, Python и ОС по снимку. Создать отдельный checkout/worktree и среду-кандидат, установить совместимые официальные компоненты, зафиксировать версии и происхождение пакетов. Не менять старую среду. Если без изменения общего драйвера кандидат не работает, остановиться и отдельно согласовать этот шаг.

### Этап C — correctness прежде скорости

Проверить загрузку HIP runtime, затем сборку native extensions и JIT, небольшие tensor/copy-проверки, затем запуск небольшой уже известной модели. Сначала eager, без одновременного включения graphs, изменения формата весов или нового cache policy.

Отдельно проверить правильность GGUF dequant/GEMM и offload-копирования, известные ответы/JSON/tool calls, повторные запросы, завершение сервера. Различие greedy-текста между стеками не всегда означает ошибку: возможны численные различия; для ядер нужны референсы и обоснованные допуски.

### Этап D — A/B-производительность

Сначала та модель и файл весов, которые уже работают. Не начинать квалификацию стека с самой тяжёлой Qwen3.8-Flash-Next.

| Фиксировать | Требование |
|---|---|
| Код | Одинаковый SHA для сравнения сред; если нужны compatibility-патчи, описать их отдельно |
| Модель | Один checkpoint, одинаковый файл/хеш, tokenizer и chat template |
| Контекст | Реальное число input tokens после токенизации, а не символы или output limit |
| Стартовые размеры | Например 1K и 4K; затем 16K/32K только при достаточной памяти |
| Ответ | Одинаковый лимит, например 256; записывать фактическое число output tokens |
| Настройки | Одинаковые offload/cache/overlap/graphs/concurrency и sampling |
| Повторения | Прогрев отдельно; затем минимум 5 сопоставимых запросов |
| Метрики | TTFT, prefill, decode, end-to-end время, peak RAM/VRAM, ошибки |
| Кэширование | Не смешивать cold prefill и reuse prefix cache; фиксировать состояние |
| Устойчивость | Отдельная длительная проверка после коротких correctness-тестов |

Не смешивать суммарную скорость нескольких запросов со скоростью одного. Не переносить чужие 31.6 tok/s на другой checkpoint/контекст/окружение. Если метрики сервера недоступны, честно обозначить клиентскую методику и не называть end-to-end throughput чистым decode.

## 6. Условия завершения миграции

Кандидат считается проверенным только после того, как корректная установка воспроизводится, native/JIT пути проходят проверки на RX 9070 XT, модель отвечает корректно, собраны A/B-результаты и длительный запуск не обнаружил сбоев. Ускорение не обязательно: результатом может быть равная скорость при лучшей совместимости или отказ от обновления из-за регрессии.

Старую среду сохранять до завершения этих проверок. При сбое остановить тестовый сервер и вернуться к старому checkout/окружению; это не отменяет отдельно сделанные изменения общего драйвера.
